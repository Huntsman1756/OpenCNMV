# G1 — design seed (not a build plan)

**Status:** framing only. G0-R closed at tag `g0-r-go` (`15c4778`), verdict `GO`,
which authorises G1 **design** — not a platform. Until the primary question below
is answered, API / UI / MCP remain prohibited, exactly as in G0.

## Primary problem

```text
LANGUAGE_VARIANT_COVERAGE_UNRESOLVED  (binding finding from R16)
```

CNMV's OAM feed carries **multiple ESEF submissions for the same issuer +
period + authority**: SAN and BBVA publish both `-es` and `-en` report packages;
ListadoIFA exposes only one ZIP per registro (the `-es` one); the external
oracle indexed the `-en` ones. These variants are **not interchangeable
translations**: BBVA's `-en` vs `-es` packages disagree on a real value
(`ifrs-full:Equity` @2023-01-01, FinancialEffectOfChangesInAccountingPolicy
member: −98M vs +98M).

The first question of G1 is therefore:

> What is the correct identity of an ESEF submission when one issuer + period +
> OAM can publish several language variants whose data are not necessarily
> equivalent?

## Model correction carried from R17

R17's canonical key included `value_sha256` — correct for proving no
CURRENT_HALF/YTD collapse, but **wrong as a fact's structural identity**. G1
separates:

```text
fact_structural_key          fact_payload
  concept QName                 value
  entity                        decimals        (precision metadata)
  period                        nil
  dimensions                    value_sha256
  unit
  language (when applicable)
```

Two records sharing a structural key but differing in payload are a
**conflict/duplicate to detect**, not two unrelated facts:

```text
same structural key + different submitted value
  → DIVERGENT_SUBMISSION_FACT        (e.g. the BBVA −98M/+98M case)
```

## Proposed model extension

```text
filing
  └─ filing_version
       ├─ submission_variant      NEW — e.g. -es, -en (language/packaging variant
       │                            of the same regulatory submission)
       │    └─ artifacts + facts
       └─ events (R13 semantics unchanged)
```

- Variants are **never silently merged** and no variant is designated "truth".
- Divergences across variants are first-class evidence.
- Prohibited public claim until resolved: *"complete CNMV/OAM ESEF coverage"*.

## First G1 investigation — G1-A result

**G1-A `OAM_VARIANT_DISCOVERY`: PASS** — `g1/G1-A-oam-variant-discovery/`.

The `-en` variants were always officially discoverable on the same CNMV
surfaces (`busqueda?id=25`, `listadoifa`): the `verdocumento` document tokens
are **interface-language dependent** — `lang=en` serves the `-en` artifact set
of the *same* registry entry, with `-es` fallback when no English filing
exists (IBE). All six in-scope registros share `nregaud`, submission
`nreg`, dates/auditor/`infadicionifa` history; per-filing verdicts:
`DUAL_VARIANT_SHARED_REGISTRY` (SAN, BBVA ×4) and
`SINGLE_VARIANT_WITH_UI_FALLBACK` (IBE ×2 — `lang=en` resolves to the `-es`
artifact set, `submitted_variant_count=1`).

Model consequence — the evidence supports `submission_variant` and
`version_event` as **orthogonal axes under filing** as the least-assumptive,
lossless provisional representation:

```text
filing (identity = nregaud)
  ├─ submission_variant   (language → artifact set)
  └─ version_event        (shared registry-level history)
```

Caveat: current evidence does **not** distinguish the lifecycle ordering —
the observed shape is still compatible with `version → {variants}` and with
`variant → versions` evolving in sync. What would falsify it is a
substitution touching one variant but not the other. Also modelled:
`requested_ui_language` (es|en) vs `resolved_submission_language` +
`resolution_mode` — a `lang=en` view resolving to the `-es` artifact set is
`FALLBACK`, not a `submission_variant` (IBE).

### G1-B `DUAL_LANGUAGE_CAPTURE`: **PASS** (`g1/G1-B-dual-language-capture/`)

Dual-language capture implemented with `variant_artifact_set_id` =
content identity of the served ESEF report package; deduplication by
served bytes, never by `requested_ui_language`. All 10 unique variant
packages parse offline under Arelle 2.44.0 with pinned taxonomies
(Control A API↔OIM multiset equal, ioerr=0).

Cross-variant comparison over taxonomy concepts (extension concepts are
`UNMAPPED_VARIANT_FACT` — empirically justified: SAN's `-es`/`-en` use
different extension namespaces, and 0 extension QNames are shared even
where the namespace matches). Outcome classes: `MATCH_EXACT`,
`MATCH_NUMERIC_EQUIVALENT`, `DIVERGENT_SUBMISSION_FACT`,
`VARIANT_ONLY_FACT`, `LANGUAGE_SENSITIVE_NOT_COMPARED`, `UNMAPPED`.

Mandatory checks all green: BBVA `Equity`@2023-01-01 es +98M / en −98M →
`DIVERGENT_SUBMISSION_FACT`; SAN `0.9`/`0.900` → `MATCH_NUMERIC_EQUIVALENT`;
IBE single-variant fallback → skipped, zero divergences, no phantom EN;
adversarial bad-model (UI language as identity) provably produces the
phantom. Determinism: two captures identical inventory, two extraction
runs identical facts, dataset rebuild identical.

This closes the binding limitation `LANGUAGE_VARIANT_COVERAGE_UNRESOLVED`
for the six in-scope ESEF filings: both language views are captured,
variant identity is content-based, and divergences are first-class
evidence. Remaining open target (G1-C+): per-variant independent
substitution (lifecycle ordering) and a defensible extension-concept
mapping via anchoring.

### G1-C `EXTENSION_VARIANT_IDENTITY`: **PASS** (`g1/G1-C-extension-variant-identity/`)

Extension elements (fact-bearing concepts **and** dimension members — the
same elements often play both roles) are paired across `-es`/`-en` purely on
structural DTS evidence extracted offline by Arelle 2.44.0: wider-narrower
anchoring sets, XBRL properties (type/periodType/balance/substGroup), and
presentation / calculation / definition (`domain-member`) path signatures.
Two-tier rule: unordered signature first; sibling `order` only disambiguates
structurally identical candidates. Verdicts: `PROVEN_EQUIVALENT` (415 of 449
elements, mutually-unique 1:1), `AMBIGUOUS` (11 — including real
shared-signature cases in BBVA-FY2025), `CONFLICT` (2), `UNMATCHED` (21).
Labels are never used; a synthetic identical-signature adversarial case
provably cannot pair.

Re-running the G1-B comparison with `pair_id` rewrites (PROVEN only):

```text
UNMAPPED_VARIANT_FACT   4,239 ->   132
VARIANT_ONLY_FACT       2,453 ->     6
MATCH_EXACT             3,549 -> 6,822
MATCH_NUMERIC_EQUIVALENT    1 ->     9
DIVERGENT_SUBMISSION_FACT   1 ->     1   (BBVA ±98M preserved; no new divergences)
```

Most of the previously unpairable mass is now deterministically reconciled;
the residue is honest (ambiguous/missing elements and real asymmetries).
Determinism: structure extraction run1==run2 byte-equal, mapping and mapped
dataset rebuilds identical.

### G1-D `VARIANT_LIFECYCLE_FALSIFICATION`: **PASS** (`g1/G1-D-variant-lifecycle-falsification/`)

Scan of 96 official ESEF filings (FY2023–FY2025, 37-issuer watchlist): 12
dual-variant filings, 8 with substitution rows — one intersection:
**TELEFONICA FY2024 `nregaud` 20484** (`DUAL_VARIANT_SHARED_REGISTRY`,
distinct `-es`/`-en` packages `cc7f2e1c…`/`f8726a6e…`).

Three submissions under one registry:

```text
nreg 2025030764  2025-02-27  original FEUE submission
nreg 2025031622  2025-02-28  substitution: adds audit report / responsibility
                             declaration / signature sheet to the INDIVIDUAL
                             accounts — silent on language
                             -> VARIANT_SCOPE_NOT_OBSERVABLE
     —           2025-03-13  substitution: "la versión en inglés publicada de
                             los Estados Financieros Consolidados … aparece
                             en español"
                             -> EN_ONLY_REPLACED
```

**Independent variant lifecycle is proven**: a `version_event` affected only
the `-en` `submission_variant`, on explicit official certificate evidence.
`variant → versions` gains strong evidence; `version → {variants}` can no
longer be the only topology. A `version_event` therefore needs an explicit
affected-artefact-set scope — it is not automatically filing-wide.

Recorded caveats: `BOTH_VARIANTS_REPLACED` was never inferred from shared
registry/date; the event label "Otra información complementaria (Otros)" hid
the decisive substitution (labels are not authoritative); CNMV serves only
current state, so whether the `-en` ZIP bytes themselves changed is not
observable (the served `-en` package keeps 27/02 internal zip timestamps —
consistent with the replaced artefact being the published consolidated XHTML
document).

## What stays fixed (G0 invariants)

- CNMV is authoritative; third parties are oracles only.
- Official bytes preserved unmodified; SHA-256 on every artifact.
- Determinism = offline reproducibility from identical raw inputs.
- `filing` / `filing_version` / `artifact` / `fact` remain separate.
- Native QName, contexts, explicit+typed dimensions, units, decimals, periods.
- H2 ≠ FY/ESEF; `submission_kind`/`submission_scope` on `filing_version`.
- No dedup by concept+period (falsified empirically: 265–532 collisions/filing).

## Out of scope for G1 design seed

API, UI, MCP, generalisation to all issuers, other document families,
security master, custom taxonomy, LLM/AI summarisation, microservices/cloud.
